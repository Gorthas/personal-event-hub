# Personal Event Hub

[English version](README.md)

> **Статус: In Progress** — архитектура и дизайн v1 завершены. Реализация ещё не начата.

Personal Event Hub — проектируемый backend-сервис на Go для приёма универсальных событий от зарегистрированных внешних источников, сохранения их истории в PostgreSQL и отправки понятных человеку уведомлений в единственный Telegram-канал.

Первым реальным источником станет GitHub Actions, но Hub принимает собственный универсальный контракт события, а не GitHub-специфичный payload.

## Зачем нужен этот проект

Системы автоматизации создают полезные события, однако они часто остаются привязаны к отдельным инструментам и не имеют общей истории. Personal Event Hub спроектирован как небольшая и явно очерченная граница между источниками событий и персональным каналом уведомлений:

```text
GitHub Actions
      |
      v
HTTP Ingestion API
      |
      v
Personal Event Hub -----> PostgreSQL
      |
      v
Telegram
```

Проект намеренно начинается с одного паттерна источника, одного канала доставки и чёткой модели ошибок. В v1 не закладываются брокер сообщений или распределённая архитектура.

## Scope v1

- Регистрация и просмотр Sources.
- Отдельный credential для каждого Source.
- Приём универсального Event с полями `title`, `message` и `occurred_at`.
- Сохранение Event до подтверждения его приёма.
- Одна синхронная best-effort попытка доставки в Telegram.
- Сохранение результата доставки, когда это возможно.
- Owner-facing история с состояниями `success`, `failed` и `not recorded`.
- Ротация credential Source без потери Source и его истории.
- Экспорт истории Source.
- Hard delete Source вместе со всеми его Events и Deliveries.

## Основная модель

```text
Source 1 ---- N Event
                  |
                  | 1
                  |
                  0..1 Delivery
```

- **Source** — зарегистрированный внешний отправитель с уникальным именем и собственным credential.
- **Event** — неизменяемый факт, принятый от аутентифицированного Source и сохранённый Hub.
- **Delivery** — записанный результат единственной попытки доставки Event в Telegram.

`Destination` и `Route` намеренно отсутствуют в v1. Все Events используют один Telegram target из конфигурации приложения.

## Контракт приёма и доставки

```text
аутентифицировать Source
        -> провалидировать входные данные
        -> сформировать Event
        -> сохранить Event
        -> один раз попытаться доставить в Telegram
        -> по возможности сохранить Delivery
        -> вернуть результат приёма Event
```

Event считается **принятым только после успешного сохранения Event**. Последующая ошибка Telegram или сохранения Delivery не отменяет факт приёма.

Source получает результат собственного контракта с Hub: был ли Event принят. Детали Telegram остаются внутренними и доступны владельцу через History.

History вычисляет состояние доставки следующим образом:

| Сохранённое состояние | Состояние в History |
|---|---|
| Delivery с `success` | `success` |
| Delivery с `failed` | `failed` |
| У сохранённого Event нет Delivery | `not recorded` |

`not recorded` — не третье значение результата Delivery. Оно означает, что Event есть, но сохранённого результата доставки нет.

## Архитектура

Дизайн разделяет ответственности, не фиксируя преждевременно framework или структуру пакетов:

- **HTTP** переводит запросы и ответы на транспортной границе.
- **Coordinator** владеет authentication, validation и порядком операций.
- **Storage** читает и сохраняет данные в PostgreSQL.
- **Telegram boundary** форматирует Event и выполняет одну попытку отправки.
- **Startup / Composition** проверяет конфигурацию, создаёт зависимости, связывает их и запускает сервис.

Подробности находятся в документах [Архитектура](docs/ru/architecture.md) и [Event Flow](docs/ru/event-flow.md).

## Модель безопасности

- У каждого Source есть отдельный credential только для ingestion.
- Management и History используют отдельный Owner credential.
- Новый credential Source раскрывается только при создании или ротации.
- Ротация делает старый credential недействительным, сохраняя Source и его историю.
- Telegram bot credential, Telegram target, настройки PostgreSQL и Owner credential относятся к внешней конфигурации приложения.
- Секреты не должны попадать в Git или логи; публичное развёртывание требует HTTPS.

Точные механизмы генерации, проверки и хранения credentials намеренно отложены до реализации Security-блока и не выдаются за готовый код.

## Гарантии и ограничения v1

Дизайн гарантирует, что Telegram не вызывается до сохранения Event, а подтверждённая ошибка сохранения Event никогда не возвращается как успешный приём.

В v1 намеренно отсутствуют:

- автоматические retry;
- recovery прерванного delivery flow;
- idempotency и deduplication;
- eventual delivery;
- строгий порядок Events или уведомлений;
- несколько Telegram targets и routing;
- ручной retry Delivery;
- история нескольких попыток доставки.

Из этих ограничений следуют известные неоднозначности при потерянном ответе, timeout и падении процесса. Они явно описаны в [Модели отказов](docs/ru/failure-model.md).
