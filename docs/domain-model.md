# Domain Model

## Status

This is the approved conceptual model for v1. It is not a SQL schema and does not prescribe identifier types, column types, table names, indexes, or migration details.

## Model overview

```text
Source
  |
  | 1 : N
  v
Event
  |
  | 1 : 0..1
  v
Delivery
```

The model contains only three domain entities: Source, Event, and Delivery.

## Source

A Source is a registered external producer that is allowed to submit Events to the Hub.

### Approved conceptual data

- stable internal identity;
- unique human-readable name;
- Source-specific credential verification data.

The exact identifier and credential representation remain implementation decisions. In particular, the conceptual presence of credentials does not imply plaintext secret storage.

### Responsibilities and relationships

- One Source can own many Events.
- Every Event belongs to exactly one Source.
- The Source is determined by successful authentication, not trusted from the Event payload.
- Source name identifies the connection to the owner and appears in history and Telegram messages.

### Lifecycle

```text
create
  -> active and usable
  -> credential may be rotated
  -> export may be requested
  -> hard delete
```

Source identity and history survive credential rotation. The old credential stops working and a new credential is disclosed once.

There is no general Source update or rename operation in v1. There is also no disable, archive, or soft-delete state.

### Deletion

Deleting a Source removes:

- the Source;
- its credential verification data;
- all Events owned by the Source;
- every Delivery associated with those Events.

No historical Source snapshot remains inside the Hub. The owner can export the Source history before deletion, but export is optional and does not alter Hub data.

## Event

An Event is the immutable internal record of a fact reported by an authenticated Source and successfully persisted by the Hub.

### Input data supplied by a Source

- `title` — required and non-empty;
- `message` — required and non-empty;
- `occurred_at` — required and structurally valid.

v1 validates the timestamp representation but does not judge whether the reported occurrence time is plausible.

### Context added by the Hub

- stable Event identity;
- authenticated Source relationship;
- `received_at`, generated by the Hub.

The resulting conceptual Event is:

```text
Event
-----
identity
Source
title
message
occurred_at
received_at
```

### Lifecycle

An Event exists as an accepted Event only after persistence succeeds. Once created, it is not edited by the owner and is not changed by later Telegram outcomes.

There is no independent Event delete operation in v1. An Event is removed only as part of hard-deleting its Source.

### Data intentionally excluded

Event does not contain:

- delivery status or error;
- Telegram configuration;
- retry count;
- severity;
- arbitrary metadata;
- the raw incoming request.

These values either belong elsewhere or have no approved v1 use case.

## Delivery

A Delivery records the known outcome of the Hub's single synchronous attempt to send an Event through Telegram.

### Approved conceptual data

- relationship to one Event;
- `result`, either `success` or `failed`;
- `attempted_at`;
- a human-readable `error` when the result is `failed`.

For `success`, no error is recorded. For `failed`, the error describes only what the Hub actually knows, such as a timeout or an explicit Telegram error. Delivery is not intended to store raw external responses, headers, stack traces, or other low-level diagnostics.

### Relationship and lifecycle

- An Event has zero or one Delivery in v1.
- A Delivery belongs to exactly one Event.
- Delivery is created only after the attempt reaches a known outcome.
- There is no `pending` Delivery state.
- A persisted Delivery is not edited and is not retried.
- Delivery is deleted with its Event.

The zero side of `0..1` is significant: a process crash or failure to store the delivery result can leave a persisted Event without a Delivery record.

## History projection

History exposes a derived state rather than changing the Delivery entity:

```text
Delivery(result = success) -> success
Delivery(result = failed)  -> failed
no Delivery                -> not recorded
```

`not recorded` does not mean pending, scheduled, or recoverable. It means only that the Hub has no persisted Delivery outcome for the Event.

## Why Destination and Route do not exist in v1

The Hub has one Telegram target configured for the entire deployment. The owner does not manage a collection of delivery destinations, and the Hub does not select among routes.

The deferred evolution is intentional:

```text
multiple delivery targets
        -> Destination becomes meaningful
        -> target selection becomes necessary
        -> routing may become meaningful
        -> Route may become justified
```

Until that need exists, Destination and Route would add a model that performs no v1 work.

## Open implementation details

The design intentionally does not decide:

- identifier types;
- SQL table or column definitions;
- exact timestamp representation;
- maximum title and message lengths;
- exact credential hashing or verification mechanism;
- export file format.

Those choices belong to the relevant implementation verticals.
